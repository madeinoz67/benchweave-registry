# benchweave-registry

The repository of record for the BenchWeave contributor publishing lane: review
records, lifecycle records, vetted publishers, lane rules, and the published,
signed releases themselves. Git-native by design — a submission is a pull
request, there is no service, and a clean clone of this repository alone is
sufficient to validate every record and verify every published release's
digests and signatures (CR-34).

Layout:

| Path | What it is |
|------|------------|
| `records/records.schema.json` | The lane-owned schema over canonical-JSON records (CR-9/CR-10/CR-56/CR-60). |
| `records/submissions/…` | Committed review records (CR-8/CR-9; PR threads stay discussion-only, Q4). |
| `records/lifecycle/…` | Publish / yank / advisory / unlist / takedown / transfer records (CR-28). |
| `records/publishers.json` | Vetted publisher identities and namespace assignments (CR-15/CR-39). |
| `index.json` + `records/index.schema.json` | THE generated catalogue/search/verification index (Q7/CR-26) and its format contract; regenerated by `scripts/generate_index.py` (CI refuses drift); the catalogue page renders it and never reshapes it. |
| `catalogue/` | The catalogue page's committed SOURCE — the template (`index.template.html`) and the search wiring + page CSS (`assets/`). The rendered page itself is NEVER committed (deploy-time artifact). |
| `vendored/gateway/` | Digest-pinned vendor copies citing gateway origins: the release-status schema (the lifecycle enum's authority) and the public-site styleguide (the catalogue's style authority). Each carries a `.pin.json`; repinning is a deliberate recorded edit. |
| `lane-rules.json` | Reserved namespaces, the similarity rule with committed vectors (CR-39), the pre-committed `scoped_transport` tier rule (Q15/CR-49), the capability enumeration (CR-45). |
| `review-checklist.md` | The versioned owner checklist with machine-citable row ids (CR-8), extending the gateway's device-developer-guide §12. |
| `releases/<registry-id>/<publisher>/<plugin>/<version>/` | The served release tree (`manifest.json`, `manifest.sig`, `status.json`, `status.sig`, `payload.zip`) — layout satisfies the gateway's `LocalDirectorySource` contract, so a clone is a resolvable origin. |
| `records/publishers.json` | Vetted publishers, their recorded public keys and key-validity windows — what publisher signatures verify against. |
| `gateway-ref` | The pinned gateway commit the admission replay runs at (Q10, F5). |
| `scripts/validate_records.py` | The records-validity gate (CI job `validity`). |
| `scripts/replay_admission.py` | On-demand admission replay through unmodified gateway admission (not a publish-time gate; the client enforces). |
| `scripts/verify.py` | Whole-clone verification: records + signatures + digests + the accountability chain (CR-54). |

## Verifying a release (two commands, nothing else)

```
git clone https://github.com/madeinoz67/benchweave-registry.git
cd benchweave-registry && uv run python scripts/verify.py
```

That prints the accountability chain for every published release — publisher,
reviewer, outcome, closure digest, capability declaration — from this clone
alone: no gateway repository, no PR thread, no running service (S3/A3).

## Publishing path (summary)

1. Package a finished plugin with `benchweave-sdk package` (the SDK CLI;
   deterministic, keyless, entry-gated — dev-lineage, mutable source refs,
   missing capability declarations, firmware without vendor attestation,
   transport declarations without triples, and publish records without a
   closure diff all refuse at packaging time with stable prefixes).
2. Open the submission with `benchweave-sdk submit` — a branch in a working
   copy of this repository plus a PR (or a printed compare URL when `gh` is
   absent). No service is required at any point (CR-6).
3. The maintainer reviews against `review-checklist.md` plus the machine
   evidence (platform findings at the pinned revision, CR-60), records the
   outcome under `records/submissions/`, and signs the accepted release with
   the maintainer-custodied key (`scripts/registry/sign_release.py` in the
   gateway repository). The review block rides inside the signed manifest
   (registry standard 0.1.2; Q2) — one signature attests release and review
   together.
4. The release RECORDS the pinned gateway version it targets
   (`gateway_ref` on the publish record, advertised in the index) — the
   registry states and advertises; the CLIENT enforces at import time
   (`scripts/replay_admission.py` is the on-demand verification tool, not a
   publish-time gate).

## The plugin catalogue (issue #224 slice 2, registry-hosted)

The public catalogue lives HERE, deployed by GitHub Pages from this
repository's `main` — there is no cross-repo mirror, no sync workflow and no
sync window (the pivot of 2026-10-02 deleted all of it). The Pages workflow,
on every push to main:

1. runs the validity job (records validity, release-status validity against
   the vendored schema, `generate_index.py --check`, the unit suite) — a red
   validity never deploys;
2. regenerates the index and renders the page from those bytes
   (`scripts/generate_catalogue_page.py --dest _site --sha "$GITHUB_SHA"`)
   — a deploy of commit X serves X's catalogue by construction;
3. runs the browser arm over the generated artifact
   (`scripts/verify_catalogue_browser.py` — DOM containment, static-render,
   honest query/empty states, no off-origin request) — a red arm never ships;
4. deploys. The page footer stamps the generating commit
   (`generated from <sha>`), so anyone can verify currency against the
   repository.

The committed tree carries the generator, the template and the wiring —
never a rendered page. Editing the template or the wiring is an ordinary PR;
the next deploy renders it. Regenerating `index.json` after a records change
stays the standing discipline (`--check` refuses drift in CI).

**No literal gate here, by stance (not omission).** This repository does NOT
adopt the gateway website's version-literal scan: `index.json` legitimately
carries version strings, and row-derived free text on the page (names,
summaries, advisory ids, source revisions) is data. The discipline is
*generation, not scanning* — the index is `--check`-pinned to the records,
the page is a deploy-time artifact derived from that index, and the page
generator refuses three-component version literals only in the STRUCTURAL
slots it stamps (template chrome, provenance stamp, card chrome). Do not
reinvent a website-style literal gate here.

**Emergency-yank window (R5, disclosed).** The PR lane lands a status change
and the index regeneration in ONE commit — the window is zero by review. A
direct push to `main` (if the branch ruleset ever allows one) carries the
window until the next regeneration-and-deploy. The documented path is a PR.

## Family conventions

Agent working rules, the memory protocol (`registry` tag), the tracker's
three-label repo taxonomy, the generated-index format contract, and the
web-surface styleguide rule (the MAIN repo's public-site styleguide) live in
[AGENTS.md](AGENTS.md) — they bind every change here.

## What this repository is not

There is no registry service (a later, explicitly-scoped effort), and nothing
here authorizes control on any gateway: publication is discovery and
provenance, commissioning stays local (REG-3). Digest verification establishes
byte integrity — never measurement truth, never intent (CR-51/NFR-S1).

## Branch protection (CR-61)

The `main` branch enforces required approvals, the records-validity and
admission-replay checks as required status checks, linear history, no force
pushes and no direct pushes — configured as a repository ruleset (see
`.github/rulesets.md` for the recorded shape; the platform owns enforcement).
